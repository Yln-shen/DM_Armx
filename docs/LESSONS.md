## §2.6 SDK 的实际形状与**四个**坑（`DM_CAN.py`）

> 原标题写的是"三个坑"，正文其实是**四个** —— 本节顺手更正。

**可用的 API（与 v0.1 假设一致 ✓）**

```python
serial_device = serial.Serial('/dev/ttyACM0', 921600, timeout=0.5)   # 注意 timeout
ctrl = MotorControl(serial_device)                                    # 收串口对象，不是端口字符串
motor = Motor(DM_Motor_Type.DM4340, SlaveID=0x01, MasterID=0x11)
ctrl.enable(motor) / ctrl.disable(motor)
ctrl.controlMIT(motor, kp, kd, q, dq, tau)          # 注意是全小写 MIT，与 control_Pos_Vel 命名不一致
ctrl.control_Pos_Vel(motor, P_desired, V_desired)
ctrl.set_zero_position(motor)
ctrl.read_motor_param(motor, RID) / ctrl.change_motor_param(motor, RID, data) / ctrl.save_motor_param(motor)
ctrl.refresh_motor_status(motor)                     # 更新 motor.isEnable
motor.getPosition() / getVelocity() / getTorque() / getError()
motor.state_err                                      # = 反馈帧 ERR 半字节，可直接用 2.5 的表解码
```

**坑 1：`control_Pos_Vel` 不可用于控制循环**
`__send_data(motorid, data)` → `sleep(0.001)` → `recv()`（:183-185）。`recv()` 是 `serial_.read_all()`（:322），而示例串口 `timeout=0.5`。**7 电机 ×500Hz 直接出局。**
→ 设计决策 D2：自构帧（`float_to_uint8s(pos)` + `float_to_uint8s(vlim)` 拼 8 字节，CAN ID = `0x100 + SlaveID`，复用类内 `send_data_frame` 模板）直接 `serial.write()`，**无 sleep、无 recv**；收帧独立轮询。

**坑 2：`DM_Motor_Type` 没有 4340P**
枚举只有 `DM4310 / DM4310_48V / DM4340 / DM4340_48V / DM6006 / DM8006 / DM8009 / DM10010L / DM10010 / DMH3510 / DMH6215 / DMG6220 / DMJH11 / DM6248P / DM3507`（:643-658）。且 `Limit_Param` 表（:86-102）里 `DM4340 = [12.5, 10, 28]`。

> **⚠️ v0.5 更正**：v0.2 在这里写「`Limit_Param` 与 4340P 手册的 40 N·m / 5.86 rad/s **不符**」——
> 这**不是矛盾，是我把两个不同的量当成同一个了**：
>
> | | 手册值 | 是什么 | 用在哪 |
> |---|---|---|---|
> | 额定 12 / 峰值 40 N·m | ✅ 手册 126-128 行 | 电机**物理能力** | 选型、动力学模型、URDF 力矩上限 |
> | 空载 56 rpm = 5.86 rad/s | ✅ 手册 130 行 | 电机**物理最高转速** | 同上 |
> | `TMAX` = 28 / `VMAX` = 10 / `PMAX` = 12.5 | ✅ 实测回读 | **MIT 帧的线性映射范围**（手册对 `0x17` 原文：*"TMAX 扭矩映射范围 RW"*） | **编解码 CAN 帧**（比例算错 = 力矩全错） |
>
> 两套数**可以且本来就应该不同**：映射范围只要覆盖得住实际用量即可，不必等于物理极限。
> 所以 SDK 表恰好等于回读值不是巧合，而是达妙给 4340 系列的默认映射范围。
> **结论不变但理由要改**：编解码一律用**回读值**（实测 12.5/10/28，与 SDK 表一致，所以不覆盖也不会错，
> 但仍应回读 —— 万一某台被改过，覆盖是唯一能发现的办法）；而算重力补偿/动力学时用**手册值**。
→ 设计决策 D5（下节）。

**坑 3：反馈帧的温度被 SDK 丢掉了**
`__process_packet` 只取 ERR/q/dq/tau 调 `recv_data(q, dq, tau, err)`（:340-360），而帧里 D[6]=T_MOS、D[7]=T_Rotor（手册:336）**没被解析**。
→ 设计决策 D6：在收帧解析里把这两个字节也存下来，温度**零总线开销**白拿。

**坑 4：`read_motor_param` 其实不重试，而且会返回旧缓存（v0.2 里写错了，此处更正）**

v0.1/v0.2 我写的是「`max_retries=20 × sleep(0.05)`，读一个寄存器最坏 ~1s」——**这是错的**。看 :523-541 的实际缩进：

```python
for _ in range(max_retries):
    sleep(retry_interval)
    self.recv_set_param_data()
    if Motor.SlaveID in self.motors_map:
        if RID in self.motors_map[Motor.SlaveID].temp_param_dict:
            return self.motors_map[Motor.SlaveID].temp_param_dict[RID]
        else:
            return None          # ← 这个 else 挂在**内层 if** 上
```

`else: return None` 是内层 `if RID in ...` 的，不在 `for` 上。而 `Motor.SlaveID in self.motors_map` 对我们永远为真（已经 `addMotor` 过）。所以：

1. **实测行为是「等 1 个 50ms，没到就返回 None」**，那个 20 次循环是死代码 —— 这解释了为什么裸用它读寄存器会时不时读到 `None`；
2. 命中缓存就**立刻返回缓存值**，不判断新鲜度 —— 拿到的是上次的旧值，调用方**无从分辨**。

→ 所以任何调用点都必须自己包装：**每次尝试前 `motor.temp_param_dict.pop(RID, None)` 清缓存，失败就重试，并把重试次数如实报出来**（重试次数本身就是链路质量指标）。`dm_bringup.py read` 与将来的 `RegisterTool.dump_pid` 都是这么做的。
→ 另外「慢」这个结论仍然成立，只是原因不是 20 次循环：每次实际读写都要等 50ms，加上 `recv_set_param_data()` 的开销。所以寄存器操作依然只能在上电/标定阶段做，绝不进控制循环。

## 五、时序类的 bug 最难查

> **本轮的教训（不是硬件的，是软件的）**：MotorBus 最容易错的不是"算错"，而是**时序** ——

> "数据慢一拍"，**极难查**。所以 `tools/smoke_dm_bus.py` 用假串口把时序钉死，其中
> [10] 特意按**真实时序**（残留帧先到、应答要等 write 之后）复现了正反两面：
> 不 flush 会拿到慢一拍的旧值。**"发之前 flush"这条规则，只有做成一个原子方法才防得住误用。**

# 重力补偿与系统辨识（2026-10-05 一整个 campaign）

> 这一节是 `AGENTS.md` 陷阱 #40~#49 的**详细叙述**。AGENTS 只留一行摘要，证据在这里。

## 七、`constraints.goal_time` 默认 0 ⇒ JTC 会**无限挂住**，不报错

**现象**：真机跑 MoveIt 轨迹，`val=-6`、机械臂停在半路。日志里没有控制器报错，只有
`Controller is taking too long to execute trajectory (expected upper bound 1.470083 s). Stopping trajectory.`

**排查过程**（值得复述，因为两次猜错都靠数据纠正）：

1. 先怀疑"加了 velocity 命令接口把 JTC 拖慢了" —— 拿 mock 同配置一跑，**0.69 s 就成功** ⇒ 接口本身不慢。
2. 又怀疑"`vlim=0.5` 卡住速度" —— 算了一下：动作最大 0.10 rad、轨迹 0.81 s ⇒ 峰值约 0.25 rad/s，
   低于 0.5 ⇒ **站不住**。
3. 于是去读 JTC 源码（`ros2_controllers` 4.42.1），链条才清楚：
   - `tolerances.hpp:check_state_tolerance_per_joint` 里
     `error_velocity = state_error.velocities.empty() ? 0.0 : ...` ⇒ **速度误差为空就恒按 0 处理**；
   - `compute_error_for_joint` 只在 `has_velocity_command_interface_ || has_effort_command_interface_`
     时才填 `error.velocities`；
   - `get_segment_tolerances` 里 `goal_state_tolerance[i].velocity = constraints.stopped_velocity_tolerance`（默认 **0.01**）；
   - 而 `goal_time` 默认 **0.0** ⇒ `if (active_tol->goal_time_tolerance != 0.0)` 不成立 ⇒
     **超时 ABORT 分支永远走不到** ⇒ 轨迹跑完但速度误差没进容差时，就**一直原地等**。
4. 真机 A/B/C 三轮坐实（同 goal、同起点、`vlim=0.5`）：

   | 轮 | 控制器命令接口 | 结果 | JTC |
   |---|---|---|---|
   | A | `[position velocity]`，无 constraints | ❌ `val=-6` | ≥1.378 s 仍未 `Goal reached` |
   | B | `[position]` | ✅ `val=1` | 0.84 s |
   | C | `[position velocity]` + 显式 constraints | ✅ `val=1` | **0.808 s** |

**结论**：①**POS_VEL 路径别声索 velocity** —— 它根本不用速度命令，声索只是平白多一条判据；
②MIT 路径声索时必须显式给 `constraints.stopped_velocity_tolerance`（实测静止速度 0.0024~0.0073，给 0.05）
与 `constraints.goal_time: 1.0`（进不了容差要**明确 ABORT**，别无限等）。

## 八、"激活时的零增益窗口" —— MIT 下 `enable()` 不给力

MIT 模式里 `Joint::enable()` 发的是**零增益零前馈**保持帧（出力恒为 0，好处是"不需要知道当前位置"）。
于是从**使能**到**第一次 `write()`** 之间，机械臂是**自由下落**的。

真机实测：`gravity_ff=true` 激活后立刻 `残差守卫触发（位置）：关节 joint4 偏离保持点 0.104 rad`。
一开始以为是守卫太紧，其实 j4 真掉了 0.104 rad（模型在那个姿态说 j4 需要 −1.98 N·m，kp=7 下静态偏 0.28 rad，
掉 0.104 rad 完全合理）。

**修法**：`on_activate` 里锁完保持目标后**立刻补一帧真实的 MIT 保持帧**。不要用"放宽守卫阈值"糊过去 ——
那会掩盖真的跑偏。修后真机复验：守卫 0 触发、3 s 前后 `/joint_states` 逐位不变。

## 九、守卫的语义必须分"保持 / 跑轨迹" —— 我在这里踩了两次

第一版守卫：`|q − q_hold| > 0.1 rad` 或 `|v| > 0.5 rad/s` ⇒ 锁存、`tau_ff` 全部置 0。

- **第一次踩**：跑轨迹时机械臂本来就要离开激活姿态 ⇒ 位置条件立刻误触发。
- **改成也查速度后第二次踩**：跑轨迹时本来就以 ~1 rad/s 在动 ⇒ 速度条件又误触发。
  表现是**j2 只走到 −0.31（目标 −0.55）、j3 几乎没动** —— 看起来像"辨识出来的模型不对"，
  其实是守卫把前馈关掉了。**这种"保护机制悄悄把事情做坏"的形态最难查**：日志里只有一条 ERROR，
  机械臂也确实"没跑飞"，很容易误判成模型问题。

最终语义：
- **保持**（命令是 NaN）⇒ 位置偏离保持点 > 0.1 rad，或 速度 > 0.5 rad/s（**且要连续 0.2 s**，宽限期 0.5 s）；
- **跑轨迹**（有命令）⇒ 只查**跟踪误差** `|命令 − 实测| > 0.3 rad`。

另外还有个更早的形态：**激活瞬间的速度采样不能直接判**。那一瞬机械臂真的在掉，速度能到 0.7~1.5 rad/s，
一个采样就锁死会让整轮数据作废（真机 scale=0.5/1.0 两轮就是这么废掉的）。

## 十、"上游 CAD 惯量不可信" —— 这是本轮最重要的发现

**怎么发现的**：做重力前馈之前，先在**张开位**（真正靠电机扛重力的姿态）用 POS_VEL 托住，
读电机反馈的保持力矩，与模型对比：

| 关节 | 模型 tau_g | 实测保持力矩 | 比值 |
|---|---|---|---|
| j2 | −0.23 | **−1.77** | 7.8× |
| j3 | −6.94 | **−5.27** | 0.76× |
| j4 | −1.99 | **−0.65** | 0.32× |

**符号全对、量级全错**，而且**不是差一个统一倍数**（7.8 / 0.76 / 0.32）⇒ 不可能是标定或单位问题，
只能是**每根连杆的惯量都不对**（上游 CAD 的连杆坐标系约定与我们实装的也不一致：辨识出的质心
"模长几乎相同、方向转了约 90°"）。

**如果直接前馈会怎样**：j4 会多发 3 倍力矩（把关节往下推）、j2 只发到 13%。

### 辨识怎么做（以及三个必须避开的坑）

重力项只跟每连杆的 **(质量, 一阶矩 m·c)** 有关，**转动惯量不影响重力** ⇒ 目标小、且对参数**线性**。

采集：POS_VEL 走 40 个静止姿态（避开硬限位/接触），每处读 `(q, effort)`。待识别参数 24 个。

**坑 1：秩亏缺 10/24 ⇒ 裸最小二乘给非物理解。**
最小范数解是 `m=0`、`质心 2.2 m` —— 拟合精度和物理解**完全一样**（都是 RMS 0.418），
但外推会很危险。用**向名义值收缩的岭回归**（λ=0.01）挑出物理的那个：精度不变、参数回到
质量 0.16~1.33 kg、|质心| ≤ 0.15 m。

**坑 2：采样必须等固件积分收敛 + 取中位数。**
第一版"停 2 s + 采一次"，重复性试验（同姿态 5 次、每次从不同方向靠近）暴露出**整块离群**：
j2/j3 同时掉了 1.3/2.5 N·m。**判据很关键**：摩擦只该作用在单个关节上、量级 0.62，
而这是两个关节**同时**掉 ⇒ 不是摩擦，是采到了瞬态。剔除离群后 j3 的极差 = 0.630 ≈ 静摩擦 0.62 ✓。
改成"停 4 s + 连采 3 次取中位数"后，RMS 从 0.515 → **0.418**。

**坑 3：固定关节的子连杆会被 pinocchio 合并进父连杆。**
本工程 `end_link`、`gripper_tcp` 都是固定关节、都并进 `link6` ⇒ 辨识出的"link6"其实是**三者的合并体**。
第一版只改 URDF 的 `link6`、没管那两个子连杆 ⇒ pinocchio 又把它们**加了一遍**（重复计入）⇒
生成出来的 URDF **反而更差**（RMS 1.03，比名义 1.32 好得有限），而且误差顺着链传到 j2/j3/j4，
**看起来像辨识方法错了**。
排查手法（推荐记住）：**把辨识参数手动设进 pinocchio 模型再比** —— 若模型对、URDF 不对，就是这一层。
修法：写回时把固定关节子连杆的惯量清零。修后 0.4177，与回归预测差 **4.6e-16**。

**最终精度**：整体 RMS **1.323 → 0.418 N·m**（留出 8 个姿态 0.411，无过拟合）。
分关节：j1 0.428（**全是**摩擦+走线，j1 轴竖直、重力恒 0）· j2 0.434 · j3 0.808 · j4 **0.070** · j5 0.094 · j6 0.094。
远端三个（4310）已经打到摩擦地板（0.145 静摩擦 ⇒ 均匀分布 RMS 0.084）；j3 高于它的地板 ⇒
j3 上有非重力的、随构型变化的载荷（走线）。

**真机端到端验证**：张开位实测保持力矩 vs 模型 RMS —— **辨识版 0.317** vs 名义版 1.096（3.5×）。

## 十一、`effort` 是电流估计，尺度必须标定

**别假设**它是 1:1。标定方法（不需要额外代码）：`gravity_ff=true` 时插件发的 `tau_ff` **就是模型算出来的已知量**，
读回 effort 与之相比即可 —— j2 1.01~1.06、j3 0.97~0.98、j4 0.85~0.88 ⇒ 往返 ≈1:1
（此前怀疑解码差 2 倍，排除）。

**它的价值**：POS_VEL 托住时固件把误差积到 ~0，此时电机报的力矩**就是真实的保持力矩** ⇒
可以直接用来校核重力模型。没有这个，"scale 该给多少"只能瞎调。

## 十二、"失能后塌回去的姿态"往往靠在机械硬限位上 —— 在那里测重力毫无意义

机械臂失能后稳定停在 `j3=+0.068`（模型上限 **+0.0508**）、`j2=+0.0008`（上限 +0.0584）——
**基本就在限位上**，重力由结构承担。

当时用 `gravity_ff` 做了四轮分级上电（scale 0.2/0.5/1.0），**全部"纹丝不动"**，
一度以为前馈算对了、符号链验证了。后来才发现：模型在该姿态说 j3 需要 **−7.27 N·m**，
而 kp=7、`tau=0` 时机械臂本该偏 **1.04 rad** 却纹丝不动 ⇒ 才意识到是硬限位撑着。
**那四轮数据对"重力补偿对不对"几乎没有信息量。**

⇒ 测重力必须换到真正靠电机扛重力的姿态（本工程用"张开位" j2 −0.55 / j3 −0.70 / j4 +0.30）。
这也顺便解释了"为什么失能后总塌回这个姿态就停住"（AGENTS 陷阱 #39）。

## 十三、构建期 xacro 不能用 `$(find <本包>)`

`arm_dynamics.urdf` 是 `arm_description` **构建时**展开的，而 xacro 里 `mit_gains_cfg` 的默认值写的是
`$(find arm_description)/config/mit_gains.yaml` —— 构建期这个包**还没安装** ⇒
`PackageNotFoundError: package 'arm_description' not found` ⇒ 整个包构建失败。
（第一次加它时"侥幸没炸"，是因为 install 里还留着上一版；和其他包一起构建就暴露了。）
⇒ CMake 的 `add_custom_command` 里**用源码路径覆盖**这些 cfg 参数，并加进 `DEPENDS`。

另外：**加了 pinocchio 之后，构建必须走 `pixi run colcon ...`**。pinocchio 进了 `dm_hardware` 的 PUBLIC
链接之后 `.so` 的链接线变了 ⇒ 在没有 `CONDA_PREFIX` 的普通 shell 里会报 `找不到 -lcap / -llttng-ust`
（陷阱 #32 的兜底只在 `CONDA_PREFIX` 存在时生效）。


## 十四、积分补不了摩擦死区 —— "高频执行的那一层"才管精度

> 这是一条**反面结论**，它推翻了我在这个工程里先说过的话（"要追平 POS_VEL 的静态精度必须加宿主侧积分项"）。
> 记录在此，因为它是个**方法论**上的坑：**同样的控制律，放在 100 Hz 的宿主里和放在 10+ kHz 的固件里，
> 效果可以完全不同。**

### 起因

MIT 模式下固件**没有积分**（τ = kp·Δp + kd·Δv + t_ff），而 POS_VEL 里固件有（`KI_ASR/KI_APR`）。
真机静态精度：MIT+重力前馈 j3 差 **0.134 rad**，POS_VEL **0.0016 rad**。差 80 倍，看起来"就是缺个积分"。

### 于是加了宿主侧积分（`ki_hold`，τ_i += ki·e·dt 加进 t_ff）

默认 0（行为不变）、误差门控（>0.15 rad 不积）、抗饱和（钳 ±0.3·torque_max 且饱和停积）、四个复位条件。
单测很漂亮：线性爬升、钳住不涨、命令跳变复位。真机跑起来也"有用" —— 但**代价是极限环**：

| ki | 三次采样跳动 max（rad） |
|---|---|
| 0 | **0**（逐位相同） |
| 0.3 | 0.010 |
| 1.0 | **0.107**（j3，6.1°） |
| 3.0 | **0.074**（j2） |

### 为什么破不了

**静态误差的本质是死区，不是"没积掉"**：稳态时 `kp·e = 摩擦力`，而摩擦力在 ±F_s 内**任意取值**
⇒ 关节可以停在目标附近 ±F_s/kp 的**任何位置**（j3：0.62/7 = 0.089 rad，与实测 0.106 吻合）。

宿主积分想破它，只能这么走：慢慢把 τ_i 爬大 → 刚超过静摩擦 → 关节**跳**一小格 → 摩擦反向 →
τ_i 又不够了 → 再爬 …… 在 **100 Hz** 下这就是个极限环，而且它的幅度就是那个死区。

**而 `kp` 是固件在电机内部按 10+ kHz 执行的** —— 它能做"亚静摩擦的连续蠕动"：力矩以极高的频率
微调，关节以肉眼看不见的速度挪过去。**同样的公式，执行频率决定它能不能破静摩擦。**

真机实测印证：kp 7→15→25，max 残差 0.0893 → 0.0591 → **0.0385**（单调）。

### 教训（可以推广的）

1. **"缺个积分"是本能的错判**：先问"误差的物理本质是什么" —— 如果是有死区的摩擦力，
   积分只在**能连续微调**的那一层才有效。
2. **控制律的作用点（宿主 vs 固件）跟控制律本身一样重要**。同一件事放到慢的那一层，
   得到的是振荡而不是精度。
3. **积分该用在哪**：补**系统性**误差（模型不准、常值偏置）很干净 —— 实测 j2 在 ki=1.0 时
   残差 0.034 → **0.0026**（降 13 倍）**且跳动为 0**，因为 j2 的偏差主要来自辨识模型的残余，不是摩擦。
4. **验收"精度"必须有重复性数据**：j3 的逐次重复性本身有 ±0.045 rad 散布（摩擦不可重复），
   单次对比在 0.05 rad 量级上不足以下结论 —— 这个量级正是我们想改善的量级。
5. **增益有硬上界，而且上界的来源不是稳定性而是"拒发"**：`kp` 大到 PD 项超过 `torque_max`
   就会拒发 ⇒ `write()` 返回 ERROR ⇒ CM 失能 ⇒ **机械臂掉下来**。所以标定 `kp` 之前
   必须先算 `torque_max / 期望滞后`（见 `AGENTS.md` 陷阱 #51）。
